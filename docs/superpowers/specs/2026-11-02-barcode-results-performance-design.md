# 条码结果页性能优化设计

## 意图

在不改变“整批准备完成后才显示结果”的前提下，减少批量结果页的 Bitmap 内存和准备耗时。重点覆盖 100 条 Code 128 与 QR；保存、分享、扫码内容和主题颜色保持现有行为。

## 现状与证据

- `ResultsContent` 在显示列表前为整批条码创建合成行 Bitmap；列表本身虽为 `LazyColumn`，行图却已全部驻留。
- Robolectric 基线在 100 条 Code 128 下测得原实现合成行约 98.1 MiB、原始图与行图合计约 141.0 MiB；100 条 QR 的合成行预计约 95.4 MiB。数据是像素分配估算，不是设备进程峰值。
- `BarcodeRenderPerformanceBaselineTest` 原实现单次基线中，100 条 ARGB 批次中位约 453 ms；滚动到末尾约 22–25 ms。仅作同环境前后比较，不代表实体机时延。
- 工作区现有的 Canvas 静区改动把 100 条 ARGB 批次测到约 342 ms，但 `BarcodePreviewTransparencyTest` 的三项暗色静区/解码测试失败；原实现下这三项通过。因此该候选不能按现状验收。

## 目标与非目标

- 保留整批原子显示：任意条码准备失败时，仍显示错误与重试；最后一项未准备完成时不显示结果工具栏或结果行。
- 结果列表不再为每条条码额外持有一张全宽合成 Bitmap；预览使用已准备的条码原图与独立文字绘制。
- 分享和保存继续按需使用现有合成导出图，导出尺寸、颜色和扫码行为不变。
- 不调整数据库、输入上限、导航语义、条码格式或签名/构建配置。

## 方案与取舍

1. **保留合成行 Bitmap，仅调整并发、尺寸和像素格式。** 改动较小，但保留主要的行图内存；RGB565 会量化主题颜色，故不作为默认方案。
2. **整批准备原始条码图，结果行由条码图与文字分别绘制。** 会改动结果行布局和位图所有权，但能保留整批就绪屏障，并移除约 95–98 MiB/100 条的合成行驻留。用户选择此方案。

## 设计

- 将结果页准备结果从合成行 Bitmap 改为持有完整批次的原始条码 Bitmap 和必要的行布局数据。全部准备成功后才发布列表；`LazyColumn` 只负责屏幕行布局，不负责延迟整批准备。
- 预览用原始条码图、居中尺寸和文字分别绘制，背景由页面绘制，以保留深浅主题颜色。行高与现有 `resultImageRowSize` 规则一致；Code 128 标签的字号、换行、间距需保持一致。
- 明确 Bitmap 是缓存共享对象还是结果页独占对象：结果页退出时不得回收缓存共享图；任何新建的独占资源必须在取消、失败和离页时释放。
- `ResultShareBridge` 保留 `composeResultRowImage` 导出路径，避免把预览优化扩展到 PNG 分享/保存。
- 现有 Canvas 静区候选先修正或撤回；只有暗色静区完全不透明、深浅主题均可解码且相关测试通过后，才可独立重新评估其性能收益。
- 并发数先维持当前值，先测新行绘制方案；仅当结果显示 CPU 争用或峰值内存仍高时，再单独比较 2、4、8 路并发。

## 验收

- 100 条 Code 128 与 QR 均保持“全部准备成功后才显示”；准备第 N 项时，结果行和工具栏仍不可见；失败、重试、取消不泄漏或误回收 Bitmap。
- 深浅主题下 Code 128、QR 等代表格式可解码；预览背景/条纹颜色、标签尺寸与现有设计一致。
- 同一 Robolectric/JDK/模拟器配置重复测量：100 条时结果页行 Bitmap 分配归零，原始图与预览的估算峰值至少比当前下降 50%；100 条批次中位准备时间目标降低 20%，10 条批次不得回退超过 10%。若测量方差超过目标幅度，先以重复结果确认再决定是否达标。
- 保存与分享仍通过既有回归测试；最终按项目规则运行完整 `verifyLocal` 门禁。模拟器结果只用于相对比较，实体设备可用后补测真实帧时和内存峰值。

## 实施状态

设计已获用户批准；结果页现已准备整批原始条码图并用 Compose Canvas 单独绘制标签与行内容。Code 128 静区保留像素复制路径并将缓冲数组从两份降为一份；Canvas 合成在 Robolectric 下未通过透明性/解码回归。Robolectric 三轮测量、API 35 模拟器 10/100 条检查和完整 `verifyLocal` 门禁均已通过。尚未在实体设备测量。
